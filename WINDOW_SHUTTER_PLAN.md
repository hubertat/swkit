# Window shutter implementation plan

Add maintained two-output roller shutter control using the existing `WindowShutterConfig` and `WindowShutter` objects in `window_shutter.go`. Integrate the device everywhere existing devices can be configured, observed, or controlled, including HomeKit, buttons, scenes, APIs, web interfaces, TUI, agent tools, and Presto.

Status: implementation plan; runtime changes are not included.

## Confirmed behavior

- `OpenDigitalOutName` and `CloseDigitalOutName` are digital outputs. The selected output stays active throughout movement; stopping deactivates both.
- There is no toggle output. Remove the remaining `toggleDout` runtime field.
- Remove the copied `withCallback` field too. The implementation polls/reconciles both outputs in `Sync` and uses its own movement timers. Where supported, subscribe to each output's `SetOnStateUpdate` to observe external changes promptly; callbacks feed the same serialized reconciliation path and never replace periodic polling. Shelly supports callbacks, while GPIO currently returns "not supported" from this method. Track registration/cleanup per output if needed; do not use a single callback flag to skip reconciliation.
- Open, Close, and Toggle are commands from the control side, including configured Button actions. Input IO belongs to Button configuration rather than the shutter itself.
- Toggle follows: start → stop → reverse direction and start → stop → repeat. Reaching an endpoint also leaves the shutter stopped, so the next toggle moves away from that endpoint.
- `OpenDurationSeconds` is the full opening time. A zero `CloseDurationSeconds` uses the opening time.
- Preserve the current device/config names and HomeKit `WindowCovering` representation.

## Proposed defaults and boundaries

These choices make the implementation concrete and can be adjusted before coding.

- Position is percentage open: 0 closed, 100 open. It is estimated from elapsed movement time, not measured.
- Startup initializes both outputs inactive and position unknown. No automatic movement on startup or reload. A full Open or Close including endpoint overrun establishes an estimated endpoint; intermediate percentage commands require a known position. Unknown position alone is not a fault; reserve faults for driver/IO errors.
- Every config save that triggers reload stops moving shutters. All replacement shutters start with unknown position until a full endpoint run completes, including shutters whose IO IDs and durations did not change. Do not transfer estimates/direction or resume movement across reload. Document this behavior in configuration editors and user documentation.
- First Toggle with unknown position starts opening. After any movement, remember its actual direction; Toggle while stopped starts the opposite direction. Stop does not reverse or clear the remembered direction. During a pending start/reversal, Toggle cancels that start and leaves the device stopped. The remembered direction remains the last direction that actually moved, not the canceled direction, so the next Toggle starts the canceled direction. If no movement has ever occurred, canceling a first pending start leaves the next Toggle's default as Open.
- Add `ReverseDelayMilliseconds` to config, with zero selecting the 500 ms default. A true zero-delay reversal is intentionally not configurable; say "0 uses 500 ms; otherwise 1–5000 ms" in field help. Verify the delay against the installed motor/controller. Retain a last-deenergized timestamp so Stop followed immediately by an opposite command also observes the delay.
- Require a motor/controller with functioning travel end limits. Add an endpoint-overrun code constant, `endpointOverrunFraction = 0.10`. For targets 0 or 100, add 10% of the full directional travel duration to the computed remaining travel time; from unknown position, run the full directional duration plus 10%. This extra time is not a config field. Intermediate targets have no overrun. Do not infer a calibrated endpoint from a relay turning off early. Later feedback/end-limit inputs can improve this model.
- Native Shelly cover RPC and physical hold-to-run inputs are follow-up work. Existing Button press events provide the requested discrete commands; press/release control would require extending the input event model.

## Stage 1 Device controller and movement state

Files: `window_shutter.go`, new `window_shutter_test.go`, `drivers/io_driver.go` only if shared helper types are necessary.

Keep constructor injection, the existing two outputs, durations, logger, accessory, and fault fields. Add explicit motion (`stopped`, `opening`, `closing`), target position, position validity, fractional position estimate, movement start time/position, last actual direction, reversal state, endpoint-overrun phase, planned stop time, movement origin (commanded or externally observed), per-output expected state/deadline/write generation, timer cancellation/generation, and closed state. Retain `currentPositionPercent` as a public snapshot value if useful, but calculate internally with fractional precision to avoid drift from repeated rounding.

Expose error-returning `Open()`, `Close()`, `Stop()`, `SetPosition(int)`, `ToggleMovement()`, and an atomic snapshot getter. Reserve `Close()` for closing the shutter. Implement `Name`, `GetUniqueId`, `Sync(force bool) error`, `InitHk`, and a separate idempotent `Shutdown() error` for lifecycle cleanup.

Movement rules:

1. Serialize output writes and command decisions. Account for elapsed motion before stopping, retargeting, or reversing.
2. Never activate both outputs. Deactivate the old direction successfully before starting its opposite, and observe the reversal delay. A failed deactivation prohibits starting the other direction.
3. Repeating an active Open command targeting 100 or Close command targeting 0 does not restart travel, reversal, or overrun timers. An Open/Close command during partial-target travel retargets to its endpoint. When idle at a known endpoint, Open at 100 or Close at 0 always starts just the endpoint-overrun interval to recalibrate. Numeric `SetPosition(p)` is distinct: repeating the accepted numeric target while moving/waiting is a no-op; while idle with known current position and target both equal to p it is also a no-op, including 0 and 100. An unknown position/placeholder must not suppress an endpoint request: SetPosition(0/100) from unknown starts a full endpoint run. Preserve command kind through dispatch rather than implementing Open/Close as unconditional aliases of SetPosition. Toggle is intentionally a discrete, non-idempotent event.
4. Compute partial travel time as full directional duration × percentage distance / 100. Unknown position permits full endpoint travel but rejects intermediate targets with an actionable error. Endpoint targets that start movement under rule 3 add `full directional duration × endpointOverrunFraction` to that remaining time, even when starting from a known partial position. For example, 20 seconds full travel and 5 seconds remaining means 7 seconds energized for an endpoint target. Clamp the estimate at 0/100 during overrun, but continue reporting the energized movement direction until the output is stopped; establish an initially unknown endpoint only after the full timed run and successful stop. Stop or reversal can interrupt overrun. Rule 3 determines whether an idle endpoint command recalibrates or is a numeric no-op.
5. Schedule target/maximum-runtime stop independently of the general sync ticker. Commanded endpoint runs are bounded by full directional duration plus overrun (and any preceding reversal wait); partial runs have no overrun. Use injectable clock and timer functions, as scenes already do. Avoid sleeping while holding a state lock.
6. A command that changes movement invalidates previous movement and reversal timers; rule 3 no-ops leave them unchanged. Timer callbacks check generation/closed state within the same command serialization used for output writes, preventing a stale callback from stopping or restarting later movement.
7. Stop attempts to deactivate both outputs even if one fails; return joined errors and mark state faulty/uncertain rather than claiming successful stopping. Position becomes unknown when movement cannot be reconstructed reliably.
8. `Sync` always advances elapsed position estimates and reconciles observed output state, including when `DisableHomekit` is true or `hk == nil`. Only characteristic publication is conditional on HomeKit initialization; do not copy existing devices' early-return pattern. APIs and snapshot readers must receive current estimates without HomeKit. Do not start opposite movement based only on an asynchronously cached off reading.
   - Define `outputPendingTimeout = 3 * time.Second`, using the injected clock. Each output independently tracks `{active, expected bool, deadline, writeGeneration}`. Before a driver write, install the expectation with deadline `now + outputPendingTimeout` and a new generation so synchronous callbacks see it. A successful write updates its deadline to completion time plus the timeout only if that generation is still active (do not reactivate an expectation already confirmed by a synchronous callback); on failure, roll back only that write's expectation if its generation is still current, and report the IO error. A newer write replaces the old expectation. A no-op command or poll must not extend deadlines.
   - In both polling and callback reconciliation, a healthy observation matching an active expectation clears it and confirms that output. A contradictory observation before the deadline is ignored for motion adoption: use the expected logical state and continue the commanded estimate. At or after the deadline, the next successful contradictory observation clears the expectation and is adopted as external state under the rules below. An unreadable/unhealthy output reports an IO error rather than a fabricated observation; it does not confirm a write. This mirrors DimmableLight's pending-level mechanism, without claiming that the driver provides observation timestamps.
   - Reconcile the pair using each output's confirmed or pending logical value, so a cached On after Stop cannot restart adopted movement inside the confirmation window. At timeout it can be adopted if the driver still reports it. Callbacks reconcile promptly; the regular Sync ticker also checks expiry. Discard callback or polling work captured before a newer write using captured generations, and ignore all callbacks after Shutdown. Expectations mask readback delay, not failed writes or physical relay interlocking; a successful deactivate write plus the reversal delay is still required before opposite activation.
   - Adopt fresh, externally observed single-direction movement into the same estimate instead of forcing an immediate stop. Account for prior motion, invalidate conflicting command/reversal timers, record the actual observed direction, and integrate from the last trustworthy position/transition time. If the transition time cannot be reconstructed reliably, position becomes unknown; an IO read error remains a separate fault. A callback carries only one output value: reconcile the output pair and avoid treating delayed confirmations of our own writes as new external movement.
   - For adopted external movement, set the directional endpoint as intended target and enforce a stop deadline no later than one full directional duration after observation. At that cap, stop both outputs and mark position unknown; external observation alone does not establish a calibrated endpoint. Expose this bounded adopted run through remaining-travel state. A subsequent explicit full endpoint command can establish position using the normal full duration plus overrun.
   - Adopt an externally observed stop as stopped, cancel movement timers, and retain only a trustworthy partial estimate; never upgrade an unexpected stop into a calibrated endpoint. Both outputs active is an invalid IO state: attempt to stop both, mark position unknown and report the IO fault. Stale/unreadable observations must not be adopted as a new movement direction.
9. `Shutdown` cancels timers, prevents further commands, and stops outputs before drivers close. It tolerates nil outputs, absent timers, partially initialized state, and repeated calls, attempting every available output even if another fails. Failed setup must also clean up any initialized shutters/outputs via `Shutdown`, never the movement command `Close`.

Acceptance: deterministic tests cover full/partial travel, asymmetric durations, endpoint overrun from known/unknown positions, no overrun for partial targets, interruption of overrun, repeat commands, retargeting, Stop, all Toggle transitions including cancellation and restart during reversal delay, unknown startup, output failures, stale callbacks, concurrent commands, and shutdown. At known idle 100, Open must run the overrun interval while SetPosition(100) must not write or schedule movement; test the symmetric closed case and numeric endpoint commands from unknown. Test callback and polling adoption of external direction/stop changes, the external-runtime cap and loss of position validity, contradictory outputs, and delayed confirmations of commanded writes. Use the fake clock to test matching confirmation, contradiction before/at/after the three-second deadline, On readback after Stop, failed-write rollback, synchronous callbacks during a write, replaced expectations, and no deadline extension from repeated polls/no-ops. Verify movement `Close` remains usable for later commands, while `Shutdown` stops movement and rejects further commands. Verify estimates and faults advance with HomeKit disabled and before `InitHk`. No path intentionally leaves both outputs active.

## Stage 2 Runtime registration and HomeKit

Files: `swkit.go`, `window_shutter.go`, `cmd/app/main.go`, setup/lifecycle tests.

- Add `WindowShutters []WindowShutterConfig` and the runtime collection. Include both IO IDs in `getAllIoIds`, resolve digital outputs after driver setup, construct shutters before scenes/buttons, and include them in `getDevices`, `getHkThings`, and controllable resolution.
- `loadSwKit` and `performReload` currently return from a failed `Setup` without closing the failed instance. Put failure cleanup inside `Setup` (for example, a deferred rollback enabled until setup succeeds), rather than depending on main to call it. Track every initialized shutter and any acquired outputs before a later operation can fail; failures during construction before appending a shutter must clean up locally. Stop all partially initialized shutters before closing initialized drivers, join cleanup errors with the setup error, and keep cleanup nil-safe. Test failures resolving the second output, constructing a later device/scene/button, and reload setup failure.
- Call each shutter's `Shutdown()` during `SwKit.Close` after scene/timed work is canceled and before IO drivers close. Block old timers, callbacks, and commands from affecting a replacement instance on reload. Reload deliberately stops motors and discards position/direction; verify saving an unrelated scene while moving has this documented effect and never resumes movement automatically.
- Use `accessory.NewWindowCovering`, stable device IDs, `DisableHomekit`, and `StatusFault`. Wire TargetPosition through `C.SetValueRequestFunc` to `SetPosition`; the pinned HAP v0.0.35 also provides `Int.OnSetRemoteValue` as an error-returning helper that installs this callback. Do not use `OnValueRemoteUpdate` for movement dispatch. Add HoldPosition for Stop. Publish CurrentPosition, TargetPosition, and PositionState from one snapshot.
- HomeKit has no unknown-percentage value. Use a consistent placeholder when position is unknown and PositionState Stopped while idle, without setting StatusFault solely for missing calibration. During a full calibration run, report the actual movement direction even while position remains unknown. Never interpret the placeholder as a calibrated position. Reserve StatusFault for driver/IO errors; rejecting an intermediate command because position is unknown is not an IO fault. Accept endpoint targets for establishing position and reject intermediate requests while unknown. Return a nonzero HAP status from `SetValueRequestFunc` on command failure: HAP invokes it before storing a changed remote value and aborts storage on failure. No characteristic rollback is needed.
- HAP `setValue` ignores equal-value writes before invoking the request callback. Keep repeated targets idempotent; publish the stopped position as the new target after an explicit successful Stop, so a later request for the abandoned target is a changed value and restarts movement. Test same-value behavior and rejection through actual characteristic remote-write requests.

Acceptance: HomeKit characteristic and setup tests verify callback routing, motion updates, unknown startup without StatusFault, IO errors with StatusFault, HomeKit-disabled operation, shutdown, and reload. Test saving an unrelated config while moving: outputs stop, replacement state is unknown, and no movement resumes. Test actual Home app behavior on hardware before release.

- Add `DeviceTypeWindowShutter`, summary count, provider state builder, and consistent index resolution. Use the same ordering in state enumeration and every indexed command path; test mixed device lists.
- Expose position, position-known/estimated status, target, motion, and both output IO IDs. Distinguish a healthy but uncalibrated device from a driver failure. Preserve zero positions in JSON; avoid `omitempty` ambiguity through pointer or nested shutter state fields.
- Include effective `OpenDurationSeconds`, `CloseDurationSeconds` (after fallback), and `RemainingTravelMilliseconds` in shutter snapshots/device state and nested command results. Remaining travel is the server-calculated time until the planned output stop, including pending reversal delay and endpoint overrun; idle with no pending start means zero. Distinguish a stopped output pair awaiting reversal from a completed/idle command so clients do not report completion during the wait. Recompute remaining travel from the injected clock for each snapshot, including unknown-position endpoint runs and bounded externally adopted movement. Clients must not infer completion solely from position reaching 0/100 during overrun.
- Add an optional nested `WindowShutter` payload to `app.ControlResult`, following the optional `SceneIndex` precedent. Include motion, target position, current estimated position, and position-known status. The command/result boundary must support returning that snapshot atomically.
- Treat `IsOn` only as a legacy compatibility value (known position greater than zero); shutter UIs use dedicated motion/position state. Unknown position must never appear as confirmed closed.
- Do not implement `Stateful` on WindowShutter: use the shutter snapshot, not `GetState() (bool, error)`, for movement/position state. Reject `set_for` on shutters at the provider and internal timed-control entry points before writes or timers are scheduled. Omitting `Stateful` alone is insufficient: `timedController.SetValueFor` currently falls back to `!state` when no prior state can be read. Add an explicit unsupported-device guard, including direct internal callers. Brightness commands also remain unsupported.
- Add ownership for both output IOs and prevent raw output toggle/set paths from bypassing shutter sequencing. Resolve a raw digital output index using the driver's `GetIoDebugSnapshot`: find the point by both index and `IoTypeDigitalOutput`, convert it to `app.IoPointDebugState` with driver name and `Type: "output"`, and pass it through `app.IoPointToId`. This reuses existing Shelly switches/lights addressing and Wago global-index translation; do not construct a config ID directly from the raw index. Use the same mapping for IO annotations and controls. Reject unmappable raw writes where ownership cannot be established. Enforce ownership in provider command paths and disable those controls in clients; `ConfiguredAs` alone is only a label.

Acceptance: provider tests verify command errors, indexes, snapshots, summary counts, unsupported operations, and raw IO ownership, including Shelly switch/light and Wago index translation. Test provider and direct internal timed-control calls: neither may write an output or create a timer for a shutter. Verify shutter results describe the accepted command, including Toggle-to-Stop and unknown position, rather than depending on `getDeviceState`/`NewState`; concurrent commands must not replace an earlier command's returned snapshot.

- Include shutters in scene device lists, button target pickers, nested-scene resolution, and action validation. Preserve existing earlier-scene ordering restrictions.

- A new scene activation cancels pending scene steps, not motion already started. Stopping a moving shutter requires an explicit Stop, Close, or position action in the new state. Acceptance: parsing/formatting, wrong-capability validation, button event routing, immediate/delayed scene control, cancellation, and rapid scene changes are covered with deterministic tests. Test new-scene/add-device Stop/Open defaults and preservation of custom states/actions.
